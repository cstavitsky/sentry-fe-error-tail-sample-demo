# OTLP split transport: deviations from Andrei's snippet

Source: Andrei Borza, getsentry/sentry-javascript#22118, comment 5892229034 (copied verbatim in `research/andrei_snippet.md`).
Our version: `frontend/src/otlpSplitTransport.js`. Each functional change is marked in the code with `DEVIATION n`. Code without a marker keeps Andrei's logic; formatting and naming may differ.

## Verified against the installed SDK (`@sentry/react` / `@sentry/browser` / `@sentry/core` 10.65.0)

- `Sentry.spanStreamingIntegration()` is exported. Its `beforeSetup` sets `traceLifecycle: 'stream'` (`browser/build/npm/esm/dev/integrations/spanstreaming.js`). It is **opt-in on 10.x**; no upgrade is required.
- In stream mode, segment spans don't become `transaction` events. `SentrySpan._onSpanEnded` emits `afterSegmentSpanEnd` and returns. `SpanBuffer` flushes a trace 500 ms after its segment ends, or 5 s after the trace's first span.
- Envelope item shape (`core/build/esm/tracing/spans/envelope.js`):
  - Header: `{ type: 'span', item_count, content_type: 'application/vnd.sentry.items.span.v2+json' }`
  - Payload: `{ version: 2, ingest_settings?, items: [...] }`
  - Each item has `trace_id`, `span_id`, `parent_span_id?`, `name`, `start_timestamp`/`end_timestamp` (seconds), `status: 'ok'|'error'`, `is_segment`, and `attributes: { key: { type, value, unit? } }`. The types are `string|integer|double|boolean|array`.
  - This is exactly what Andrei's `toOtlpValue`/`toOtlpSpan` expect.
- **Standalone v1 spans still exist in stream mode.** `_isStandaloneSpan` spans (e.g. INP web vitals) go through `createSpanEnvelope()`. They arrive as `[{type:'span'}, SpanJSON]`, with no `items` and fields named `description`/`data`/`timestamp`. Andrei's `flatMap(([, c]) => c.items)` yields `undefined` for them, and `toOtlpSpan(undefined)` then throws. See deviations 3 and 3b.
- **Span envelopes are span-only.** Both `SpanBuffer` and `createSpanEnvelope()` build envelopes that contain nothing but `span` items. Error, replay and log items travel in their own envelopes.
- Error events always carry `contexts.trace.{trace_id, span_id}`. When no span is active, these come from the scope's propagation context. After a page-load span ends, `browserTracingIntegration` keeps the page-load `traceId` in that propagation context (`beforeSpanEnd` → `setPropagationContext`). This is why the S6 error marker lands on the page-load trace.
- Replay's `handleAfterSendEvent` ignores responses without a 2xx `statusCode`. That handler only runs for events, which always go through the real Sentry transport. Span envelopes are sent with `client.sendEnvelope`, not `sendEvent`. Deviation 5 is therefore defensive.
- `makeFetchTransport` (`browser/.../transports/fetch.js`) sets `keepalive` only while its own pending bytes stay ≤ 60 000 (and < 15 requests). The browser's 64 KiB keepalive quota is shared by every keepalive request of the document. See deviation 2.
- The Breadcrumbs integration only skips `fetch` URLs containing `sentry_key`. The OTLP export uses the global `fetch`, so it would create `fetch` breadcrumbs. Returning `null` from `beforeBreadcrumb` also keeps it out of Replay, because `addBreadcrumb` returns before emitting `beforeAddBreadcrumb`, which is the hook Replay listens to (`core/build/esm/breadcrumbs.js`). See the note under "Outside the transport".

## Deviations

| # | Change | Why |
|---|---|---|
| 1 | `COLLECTOR_URL` is `collectorUrl` (default same-origin `'/otlp'`). nginx proxies `POST /otlp/v1/traces` to `collector:4318/v1/traces`. | The collector needs no CORS config and is not exposed publicly. The browser only talks to its own origin. |
| 2 | **Keepalive only while the page is hidden, within a 5 536-byte budget.** When `document.visibilityState === 'hidden'` (the `pagehide`/`visibilitychange` flush), OTLP bodies are chunked to ≤ 5 536 B and use `keepalive` while the OTLP keepalive bytes in flight stay ≤ 5 536 B; the rest is sent without keepalive. While the page is visible, OTLP never uses keepalive and chunks are ≤ 60 KiB. | Browsers cap the *total* in-flight keepalive body size of a document at 64 KiB, and the request that crosses it fails with a network error. Sentry's own transport may use up to 60 000 B of that, so 65 536 − 60 000 = 5 536 B is the only share that can never make a Sentry error or replay request fail. Andrei's version sent one unbounded keepalive request per envelope. The first version of this file kept its own 60 KiB budget, which together with Sentry's could exceed the quota and drop Sentry requests (`tests/local/keepalive_quota.mjs` reproduced that). Tradeoff: FE spans are best-effort at page unload. |
| 3 | Span items are read with `c.items` if it's an array, `[c]` for a v1 item without `items`, and nothing otherwise. Each span is converted in its own `try/catch`, and all OTLP work (conversion, chunking, posting) is wrapped in another one. | A v1 standalone span item or one malformed span must not throw inside `send()`. Because span envelopes are span-only, the realistic loss without this is the whole span batch of that envelope (and an exception thrown inside the SDK's flush timer), not error/replay/log items. |
| 3b | `normalizeSpan()` maps the v1 standalone span shape (`description`, `op`, `data`, `timestamp`) to the v2 shape before `toOtlpSpan()`. Plain `data` values get a type through `typeof`. Status: `ok`, `cancelled` or missing → ok, anything else → error, the same as the SDK's own v1 → v2 mapping (`spanJsonToStreamedSpan`). | INP and other standalone spans are still sent as v1 items in 10.65 stream mode (see above). Without this, they would be dropped. An earlier version mapped `cancelled` → error; aligned with the SDK so cancelled requests don't pull traces in. |
| 4 | **Error marker span.** For every `event` item that is an error (`exception`, or level `error`/`fatal`), the transport also emits one OTLP span. It has `name: 'sentry.error_marker'`, `status: ERROR`, `traceId`/`parentSpanId` from `event.contexts.trace`, a random `spanId`, a zero duration at `event.timestamp`, and the attributes `sentry.event_id`, `sentry.project=fe`, `exception.type` and `exception.message`. This happens for every envelope, including ones that contain no span items (error envelopes never do). The event itself still goes to Sentry unchanged. The collector drops marker spans after the sampling decision (`filter/drop_error_markers`). | Browser errors are Sentry events, not spans, so a tail sampler cannot see them otherwise. It only works while the collector hasn't decided the trace yet: within `decision_wait` of the trace's **first** span reaching the collector. **This is our addition, not part of Andrei's approach.** |
| 5 | A span-only envelope resolves `{ statusCode: 200 }` instead of `{}`. | SDK hooks that inspect the transport response treat a missing `statusCode` as failure. Low risk either way (see above). |
| 6 | Resource attributes are configurable: `service.name` (default `demo-frontend`), `deployment.environment` + `deployment.environment.name`, `service.version` (release), `telemetry.sdk.name/language/version`, plus `extraResourceAttributes`. A `scope` `{ name, version }` is also set. | Andrei hard-coded `service.name: 'frontend'`. The collector routes to the Sentry FE project on `service.name`. |
| 7 | *Kept:* status is `error` → 2, otherwise 0 (UNSET). | The tail sampler only matches ERROR. Mapping `ok` → 1 would add nothing. |
| 8 | *Not in the transport:* `propagateTraceparent: true` and `tracePropagationTargets: [/^\/api\//, /^\/graphql\//]` are set in `Sentry.init` (`frontend/src/sentry.js`). | Andrei's example omits them, but the OTel backend needs the W3C `traceparent` to continue the browser trace. |
| 9 | `onExport` debug hook (optional) and `__test__` export. | Used only by the local harnesses. No effect in production. |
| 10 | **OTLP sanitising.** Spans with a missing or invalid `trace_id` (not 32 hex, or all zeros) or `span_id` (not 16 hex, or all zeros), or with non-numeric timestamps, are skipped. An invalid `parent_span_id` is dropped (the span becomes a root). Attribute values: `null`/`undefined` → attribute dropped; objects and other non-primitives → `JSON.stringify` (falling back to `String()` for circular values); `NaN`/`±Infinity` → string; integers only as `intValue` when they are safe integers; array elements that aren't primitives → stringified; unknown types → string. | The collector's OTLP/JSON decoder rejects the **whole request** for one invalid value, which loses every span in that chunk, including other traces' spans and error markers. SDK-produced spans are almost always fine; this matters for spans with custom attributes. |
| 11 | Imports from `@sentry/react` instead of `@sentry/browser`, and the factory is **curried**: `transport: makeOtlpSplitTransport({ collectorUrl, serviceName, ... })` instead of Andrei's `transport: makeOtlpSplitTransport`. | The app uses `@sentry/react`, which re-exports the same functions. The config object carries the collector URL and resource attributes. |
| 12 | Option `httpClientErrorsAsUnset` (default `false`): when `true`, `http.client` spans with status `error` and a 4xx `http.response.status_code` are sent as UNSET. | The SDK marks 4xx `http.client` spans as `error`, so every 401/404 would make the tail sampler keep the trace. Default off, to keep the SDK's semantics. |
| 13 | `flush(timeout)` waits for Sentry's own buffer **and** for in-flight OTLP exports, with the same timeout. It resolves `false` if either didn't finish. | `Sentry.flush()` drains the span buffer through `send()`, which only starts the OTLP POSTs. Without this, `await Sentry.flush()` (tests, before a redirect, Electron/extensions) resolved before the spans were delivered. Andrei delegated `flush` to the Sentry transport only. |

Unchanged from Andrei's snippet:
- the `toNano` logic and `kind` CLIENT for `http.client`, INTERNAL otherwise
- wrapping `Sentry.makeFetchTransport`, which keeps Sentry's rate-limit handling and buffering
- non-span items forwarded with the original envelope headers
- `Sentry.suppressTracing` around the export `fetch`. In stream mode this is **required**: without it the export `fetch` creates a new root `http.client` span (core fetch instrumentation emits spans even without a parent), which is streamed, exported again, and so on, in an endless export loop.

## Outside the transport (`frontend/src/sentry.js`)

- `beforeBreadcrumb` drops `fetch` breadcrumbs for `{collectorUrl}/v1/traces`. Otherwise every error event carries `POST /otlp/v1/traces` breadcrumbs and Replay's Network tab shows every export.
- `tracesSampleRate: 1.0` is required by the design (the collector samples). See README "Known limitations".

## Not done (on purpose)
- No `transaction` → OTLP conversion. Stream mode doesn't produce transactions. A customer who can't enable `spanStreamingIntegration()` would need it (map the transaction and each of its `spans` to OTLP spans).
- Web vitals are not re-mapped. Whatever the SDK puts on span attributes passes through as OTLP attributes; v1 `measurements` (e.g. `inp`) are not copied (not verified which vitals are present).
- No retry and no gzip for OTLP posts. Failures are swallowed (`.catch(() => {})`) so they can never affect Sentry delivery.
